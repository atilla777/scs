# Инструкции проекта

Общаться с пользователем по-русски.

## Контекст и документы

- Конфигурация RIS: `ris.yaml` в корне этой рабочей копии.
- Основная рабочая копия этого проекта: `/home/aleksei/plums/scs`.
  Это согласованный локальный путь, а не путь для переносимого продукта.
  В другой копии проверять принадлежность к этому репозиторию и актуальность
  основной копии через `ris-proj-op-resolve-context`, не выбирать её по порядку
  списка Git worktree или по наличию `.sdlc/`.
- Продуктовая основа: `docs/product/index.md`; требования сохранены без изменений
  при согласованном переносе бандла в `docs/product/`.
- Нормативные правила: `docs/rules/index.md`, архитектура —
  `docs/rules/architecture/principles.md`, инженерные правила —
  `docs/rules/development.md`. Учитывать указанные там отложенные решения:
  наличие правил само по себе не означает готовность к реализации.
- Решение об объёме и проверенные результаты настройки:
  `docs/ris-initialization.md`.

## Маршрутизация обычных запросов

Применять соответствующий установленный skill и его ограничения даже без
slash-команды. Само упоминание работы не разрешает запись или полный цикл.

- Вопрос о RIS: `ris-proj-op-show-help`; вопрос сам по себе не является задачей.
- Обзор плана: `ris-proj-op-show-plan`; подсказка продолжения конкретной работы:
  `ris-proj-op-suggest-continuation`. Не начинать рекомендуемую работу автоматически.
- Неподтверждённое сообщение о дефекте: `ris-proj-op-register-bug`.
- Расследование зарегистрированного дефекта по точному ID:
  `ris-proj-op-investigate-bug`.
- Явно разрешённое исправление зарегистрированного дефекта:
  `ris-proj-flow-fix-bug`, только при достаточных сохранённых входах.
  Упоминание дефекта, инициализация или claim не заменяют сохранённую пару
  отчёт/критерии, входной снимок, необходимое принятие дизайна и разрешения
  на исполнение и публикацию.
- Для расследования различать доступность исследования, сохранения отчёта и
  готовность исправления. Обычное сохранение требует назначенного исследователя,
  разрешённых нативных записей, свежего сравнения, сохранения исходного и чужого
  содержимого и чтения результата; обязательный CAS-провайдер не нужен.
  Это организационный контроль, не изоляция конкурентных записей. Конфликт
  или отсутствие прав может блокировать сохранение, но не само исследование.
- Формирование roadmap: `ris-proj-op-plan-roadmap`; подготовка фичи:
  `ris-proj-flow-prepare-feature` — только по соответствующему запросу.
- Полный запуск готовой задачи: `ris-proj-flow-execute-task`; ясная ограниченная
  работа: `ris-proj-flow-execute-simple-task`. Не выбирать очередь или запускать
  полный цикл, если пользователь этого не просил; не выдумывать ID.
- Ревью изменения: `ris-proj-op-review-task`; публикация:
  `ris-proj-op-publish-task`, с разрешением пользователя и обязательными проверками.
  Запрос выполнить полный цикл задачи включает коммит, прямой push проверенного
  результата в установленную основную Git-ветку и отдельную публикацию истории
  проектного Beads/Dolt в установленный remote. Повторного подтверждения этих
  действий не требовать, если пользователь явно не ограничил работу локальным
  результатом. Это не отменяет независимое ревью, проверки исходящей истории
  и удалённое подтверждение публикации; неизвестный адрес, конфликт или отсутствие
  доступа требуют конкретного решения, а не обхода проверок.
- Изменение продуктовой основы, архитектурных и инженерных правил:
  соответствующие `ris-proj-op-author-product-foundation`,
  `ris-proj-op-author-architecture-rules`, `ris-proj-op-author-development-rules`.
  Их содержание принимать отдельно от разрешения настроить проект.

Не требовать инициализации RIS для посторонних вопросов. Сохранять входные
условия, полномочия и точку остановки каждого владельца операции.

## Локальный трекер и границы текущей настройки

Beads: выбранный проектный workspace, backend Dolt embedded, префикс `scs`.
Использовать `ris-proj-adapter-beads-tasks`; не подменять его глобальной базой
и не редактировать `.beads/` напрямую. Обычные изменения записей выполняются
с `--sandbox` по контракту адаптера. Публикация Dolt — отдельная операция после
локальных записей; разрешение полного цикла распространяется на общую историю
этого проекта, включая записи других исполнителей по согласованным работам.
Известные посторонние записи вне согласованного объёма требуют уточнения.
Публикация Git сама по себе не подтверждает публикацию Dolt, и наоборот.

`docs/ris-initialization.md` описывает исторический результат начальной локальной
настройки, а не текущий статус публикации или запрет последующих согласованных
работ. Текущие Git- и Dolt-публикации проверять по живым remote и квитанциям;
служебный коммит `bd init` сам по себе не даёт разрешения на другие работы.
Глобальные настройки, remote и hooks не менять без согласования.

Для нового исполнения задачи агент самостоятельно формирует уникальный actor
сеанса, например `opencode-<task-id>-<session-suffix>`, и явно передаёт его
в операции Beads. Спрашивать имя actor у пользователя не нужно. При продолжении
работы сначала проверяются сохранённый actor, назначение и принадлежность
исполнения; спорное владение или передача чужой задачи требуют решения
пользователя. Имя пользователя ОС, Git author и owner записи не подтверждают
владение исполнением.
