# Функциональные требования

[← Индекс](index.md)

Все обозначения CLI ниже — **предлагаемый пользовательский интерфейс**, а не команды, уже существующие в SuperCollider. Разделение на этапы не отменяет целевые требования.

## Техническая компетенция агента

### FR-01. Знание языка и среды — MVP
Агент умеет писать, читать, исправлять и объяснять программы `sclang`, использовать типичные примитивы синтеза и событий (`SynthDef`, UGens, Patterns/Events, Buffers, Buses и др.), выбирать корректный режим исполнения. Основной `SKILL.md` содержит компактный порядок работы и указания, какие справочные материалы загружать по необходимости. В пакете есть проверенные минимальные примеры. Творческие правила музыки не включать.

### FR-02. Диагностика окружения (`doctor`) — MVP
Находить исполняемые файлы `sclang`/`scsynth`, проверять версии и реальную исполнимость, необходимые предпосылки NRT, наличие локальной справки. Разрешать явное указание путей. Отличать отсутствующие обязательные компоненты от опциональных. Давать конкретные рекомендации по исправлению.

### FR-03. Локальная документация (`docs search/show`) — MVP
Находить и читать локальные материалы, соответствующие установленной версии, включая описания классов и методов. Сохранять ссылки на проверенный первоисточник и не представлять неподтверждённые сигнатуры как достоверные. При отсутствии справки сообщать об ограничении и использовать встроенные примеры и проверку выполнением. Интернет не обязателен.

### FR-04. Запуск программ (`run`) — MVP
Принимать конкретный `.scd`, запускать управляемый `sclang`, собирать вывод и диагностику, контролировать тайм-аут и завершение дочерних процессов. **Контракт завершения должен быть явным:** произвольный скрипт может оставаться активным или сообщать об ошибке, не завершая интерпретатор. CLI должен отличать успех от неполного исполнения, ошибки программы и собственной ошибки обёртки.

### FR-05. Офлайн-рендеринг (`render`) — MVP
Создавать аудио через штатный механизм NRT (`Score` / `recordNRT` или эквивалент). Иметь документированный контракт NRT-исходника/шаблона и параметры целевого результата: путь, длительность, sample rate, каналы, формат. **Не обещать преобразование произвольного realtime `.scd` в NRT.** NRT не наследует ресурсы запущенного realtime-сервера: необходимые SynthDefs и данные должны быть представлены в офлайн-задаче. Дожидаться реального завершения, проверять результат и возвращать ошибки.

### FR-06. Инспекция аудио (`audio inspect`) — MVP
Читать аудиофайл и выдавать его формат, длительность, sample rate, каналы, пиковый уровень, интервалы тишины, информацию о нечитаемых или нечисловых значениях (если применимо к представлению). Результат — компактные машинно-читаемые данные; тяжёлую визуализацию не запускать по умолчанию.

### FR-07. Проверка аудио (`audio validate`) — MVP
Сверять аудио с требованиями вызывающего агента (длительность и допуск, каналы, частота дискретизации и т.п.). Выявлять клиппинг, неожиданную тишину и резкие границы сигнала по **настраиваемым** правилам. Возвращать временные отметки и отличать критическую ошибку от предупреждения: тишина или искажение могут быть намеренными. Не оценивать музыкальный вкус.

### FR-08. Диагностическая визуализация (`audio plot`) — MVP, по запросу
По запросу создавать отдельные изображения звуковой волны, спектрограммы и/или динамики уровня по времени по явно заданным путям. Отсутствие необязательной библиотеки графиков не должно ломать стандартный рендеринг; сообщать понятную ошибку для самой команды визуализации. Не запускать AI-модель анализа аудио.

### FR-09. Самопроверка (`self-test`) — MVP
Проверять исполнение корректного и намеренно некорректного кода, NRT, аудиопроверку, тайм-ауты и корректную очистку ресурсов. Выдавать `pass`/`fail`/`skip` для каждого теста. Не требовать физического аудиоустройства и не менять посторонние проектные файлы.

### FR-10. Управляемые интерактивные сессии — после MVP
Создать сессию `sclang`, выполнить ряд команд с сохранением состояния, получить ответ по каждому запросу, узнать статус и завершить. Обеспечить идентификатор, последовательность исполнения, тайм-ауты, безопасное освобождение ресурсов и обработку падения. При необходимости управлять realtime `scsynth`; отдельно указывать предпосылки аудиобэкенда. Не строить полноценный сервер многопользовательских сессий.

### FR-11. Расширения — после MVP
Обнаруживать Quarks, дополнительные классы и UGen-плагины, проверять доступность в текущем окружении, документировать необходимые зависимости. Предпочитать базовый SuperCollider там, где это разумно. Предлагать установку/обновление сторонних компонентов только после разрешения пользователя.

### FR-12. Управляемая установка и настройка — основное поведение
При проблеме диагностировать её и сформулировать план исправления. Установка, обновление и изменение конфигурации системы допускаются только после согласования. Использовать штатные средства ОС, затем повторять диагностику и самопроверку. Не включать собственный установщик SuperCollider как обязательную составляющую.

## Иллюстративный интерфейс CLI

```bash
sc-tool doctor --json
sc-tool docs search SynthDef --json
sc-tool docs show SynthDef
sc-tool run --source program.scd --timeout 30 --json
sc-tool render --source score.scd --output final.wav --duration 30 --sample-rate 48000 --channels 2 --json
sc-tool audio inspect final.wav --json
sc-tool audio validate final.wav --duration 30 --tolerance 0.05 --json
sc-tool audio plot final.wav --kind waveform --output waveform.png
sc-tool self-test --json
# После MVP:
sc-tool session start
sc-tool session eval --id SESSION --file fragment.scd
sc-tool session stop --id SESSION
```

Конкретные имена ключей и устройство модулей — решение этапа проектирования, если внешнее поведение сохраняется.
